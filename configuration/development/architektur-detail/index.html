    🏗️ Detaillierte Architektur-Dokumentation¶

    Diese Dokumentation beschreibt die detaillierte Architektur des ClansCore-Systems, einschließlich aller Schichten, Komponenten, Datenflüsse und Design-Entscheidungen.

    System-Übersicht¶

    ClansCore ist ein monolithisches Monorepo-System für die Verwaltung eines Gaming-Clans mit folgenden Hauptkomponenten:

    • clanscore-api: REST API Backend (Node.js/Express/TypeScript)
    • dashboard: Web-Frontend (Angular/TypeScript)
    • discord-bot: Discord Bot für Community-Interaktion (Node.js/Discord.js)
    • shared: Gemeinsames Package für DTOs, Fehlerbehandlung und Utilities

    Technologie-Stack¶

    Komponente Technologie Version
    Backend API Node.js, Express, TypeScript Node.js 18+, Express 5.x
    Frontend Angular, TypeScript Angular 17+
    Discord Bot Discord.js, TypeScript Discord.js 14.x
    Datenbank MongoDB MongoDB 8
    Container Docker, Docker Compose -
    Package Manager npm Workspaces -

    Architektur-Pattern¶

    Clean Architecture / Hexagonal Architecture¶

    ClansCore folgt dem Clean Architecture Pattern mit klarer Trennung der Verantwortlichkeiten:

    ┌─────────────────────────────────────────────────────────────┐
│                    Presentation Layer                       │
│  (HTTP/REST, Controllers, Routes, Middleware)              │
│  - Express.js Router                                        │
│  - Request/Response Handler                                 │
│  - Input Validation                                         │
│  - Error Handling                                           │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                    Application Layer                        │
│  (Use Cases, Business Logic, Services)                      │
│  - User Service                                             │
│  - Gamification Service                                     │
│  - Event Service                                            │
│  - Notification Service                                      │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                      Domain Layer                            │
│  (Entities, Value Objects, Domain Logic)                    │
│  - Person, Role, UserRole                                    │
│  - Task, TaskParticipant, TaskType                          │
│  - Event, EventParticipant, Calendar                        │
│  - Transaction, Leaderboard, Reward                          │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                  Infrastructure Layer                        │
│  (Database, External Services, Adapters)                   │
│  - MongoDB Integration (Mongoose)                            │
│  - Discord API Integration                                  │
│  - Google Calendar Integration                               │
│  - Notification Adapters                                    │
└─────────────────────────────────────────────────────────────┘

    Dependency Rule¶

    Die Dependency Rule besagt: - Innere Schichten kennen keine äußeren Schichten - Abhängigkeiten zeigen nach innen - Domain Layer hat keine Abhängigkeiten zu anderen Schichten - Infrastructure Layer implementiert Interfaces aus Application/Domain

    Workspace-Konfiguration¶

    Das Projekt nutzt npm Workspaces für die Verwaltung mehrerer Packages:

    {
  "workspaces": [
    "apps/*",
    "shared"
  ]
}

    Vorteile: - Zentralisierte Dependency-Verwaltung - Einfache Cross-Package-Referenzen - Konsistente TypeScript-Versionen - Einfaches Build-System

    Presentation Layer¶

    Verantwortlichkeiten: - HTTP-Request/Response-Handling - Input-Validierung - Authentifizierung/Autorisierung - Error-Handling - Route-Definition

    Komponenten:

    1. Routes (presentation/routes/)
    2. Definieren API-Endpunkte
    3. Verknüpfen HTTP-Methoden mit Controllern

    4. Middleware-Registrierung

    5. Controllers (presentation/controllers/)

    6. Extrahieren Request-Daten
    7. Rufen Application Services auf
    8. Transformieren Responses

    9. Fehlerbehandlung

    10. Middleware (presentation/middleware/)

    11. Error Middleware: Globaler Error Handler
    12. Validation Middleware: Request-Validierung
    13. Auth Middleware: JWT/API Key Validation

    Beispiel-Flow:

    // Route Definition
router.post("/tasks", validateTaskInput, createTask);

// Controller
async function createTask(req: Request, res: Response) {
    const result = await taskService.createTask(req.body);
    if (!result.ok) {
        return sendError(res, result.error);
    }
    return res.status(201).json(result.data);
}

    5. Value Objects

    async findById(id: string): Promise<Result<Person>> {
        try {
            const person = await Person.findById(id);

        }

    Kommunikations-Patterns¶

    1. API ↔ Discord Bot (Webhooks)¶

    Pattern: Webhook-basierte Kommunikation

    Flow: 1. clanscore-api sendet HTTP POST Request 2. Discord Bot empfängt Webhook 3. Verarbeitet Event 4. Aktualisiert Discord

    Authentifizierung: - Header: x-webhook-token: <WEBHOOK_SHARED_SECRET> - Validierung im Discord Bot

    Webhook-Endpunkte: - POST /api/notifications/user-status - Benutzer-Status-Änderungen - POST /api/notifications/role-changed - Rollen-Änderungen - POST /api/notifications/role-updated - Rollen-Updates

    Beispiel:

    // clanscore-api
await fetch(`${DISCORD_BOT_WEBHOOK_URL}/api/notifications/role-changed`, {
    method: "POST",
    headers: {
        "Content-Type": "application/json",
        "x-webhook-token": WEBHOOK_SHARED_SECRET,
    },
    body: JSON.stringify({
        discordId: event.platformUserId,
        addRoles: event.addedRoles,
        removeRoles: event.removedRoles,
    }),
});

    2. Dashboard ↔ API (REST)¶

    Pattern: RESTful API

    Authentifizierung: - JWT Tokens: Für authentifizierte Benutzer - API Keys: Für Service-to-Service Kommunikation

    CORS-Konfiguration: - Erlaubte Origins: Konfigurierbar via CORS_ORIGIN - Credentials: Unterstützt

    Beispiel:

    // Dashboard Service
this.http.post<CreateTaskResponse>(
    `${this.apiUrl}/tasks`,
    taskData,
    {
        headers: {
            'Authorization': `Bearer ${this.authToken}`,
        },
    }
);

    3. Discord Bot ↔ API (REST)¶

    Pattern: RESTful API mit API Key

    Authentifizierung: - Header: x-api-key: <CLANSCORE_API_KEY>

    Beispiel:

    // Discord Bot API Client
const response = await fetch(`${CLANSCORE_API_URL}/tasks`, {
    method: "GET",
    headers: {
        "x-api-key": CLANSCORE_API_KEY,
    },
});

    Sicherheits-Architektur¶

    Authentifizierung¶

    1. JWT Tokens (Dashboard)¶

    Flow: 1. Benutzer loggt sich ein (POST /api/auth/login) 2. API validiert Credentials 3. API generiert JWT Token 4. Token wird im Cookie gespeichert 5. Nachfolgende Requests enthalten Token im Header

    Token-Struktur: 

    {
    userId: string,
    username: string,
    roles: string[],
    iat: number,
    exp: number
}

    Validierung: - Middleware: extractUser extrahiert User aus Token - Route Guards: Prüfen Authentifizierung

    2. API Keys (Service-to-Service)¶

    Verwendung: - Discord Bot → clanscore-api - Externe Services → clanscore-api

    Validierung: - Header: x-api-key: <CLANSCORE_API_KEY> - Middleware: validateApiKey

    3. Webhook Secrets¶

    Verwendung: - clanscore-api → discord-bot

    Validierung: - Header: x-webhook-token: <WEBHOOK_SHARED_SECRET> - Vergleich im Discord Bot

    Autorisierung¶

    Rollen-basiert¶

    Rollen: - Mitglied: Basis-Zugriff - Vorstand: Erweiterte Rechte - Admin: Vollzugriff

    Implementierung: - Middleware: Prüft User-Rollen - Route Guards: Schützen Endpunkte - Discord Permissions: Bot-Commands

    Permission Checks¶

    // Beispiel: Permission Check
function requireRole(role: string) {
    return (req: Request, res: Response, next: NextFunction) => {
        if (!req.user?.roles.includes(role)) {
            return sendError(res, err(ErrorType.PermissionDenied));
        }
        next();
    };
}

    Sicherheits-Maßnahmen¶

    1. Password Hashing: bcrypt (10 Rounds)
    2. HTTPS: In Production (via Nginx)
    3. CORS: Konfigurierte Origins
    4. Helmet: Security Headers
    5. Input Validation: Zod Schemas
    6. SQL Injection Prevention: Mongoose (kein SQL)
    7. XSS Prevention: Angular Escaping, Helmet

    Design-Entscheidungen¶

    1. Clean Architecture¶

    Entscheidung: Clean Architecture mit klarer Schichtentrennung

    Begründung: - Testbarkeit: Jede Schicht isoliert testbar - Wartbarkeit: Klare Verantwortlichkeiten - Erweiterbarkeit: Neue Features ohne große Refactorings

    2. Monorepo¶

    Entscheidung: npm Workspaces für alle Apps

    Begründung: - Code-Sharing: Gemeinsames shared Package - Konsistenz: Einheitliche Dependency-Versionen - Einfache Entwicklung: Alle Apps im gleichen Repo

    3. MongoDB¶

    Entscheidung: MongoDB als Datenbank

    Begründung: - Flexible Schema: Anpassbar an Anforderungen - Document-Model: Passt zu Domain-Entities - Einfache Integration: Mongoose ODM

    4. Adapter-Pattern (Notifications)¶

    Entscheidung: Adapter-Pattern für Benachrichtigungen

    Begründung: - Erweiterbarkeit: Neue Plattformen einfach hinzufügbar - Entkopplung: Application Layer kennt keine Details - Testbarkeit: Adapter isoliert testbar

    5. Result-Pattern (Error Handling)¶

    Entscheidung: Result-Type für Fehlerbehandlung

    Begründung: - Type-Safety: Fehler explizit im Type-System - Keine Exceptions: Vorhersehbare Fehlerbehandlung - Konsistenz: Einheitliches Error-Handling

    Beispiel: 

    type Result<T> = 
    | { ok: true; data: T }
    | { ok: false; error: ErrorDetails };

    6. DTOs (Data Transfer Objects)¶

    Entscheidung: Separate DTOs für API-Kommunikation

    Begründung: - API-Stabilität: Domain-Änderungen beeinflussen API nicht - Validierung: Zod-Schemas für Input-Validierung - Dokumentation: DTOs dokumentieren API-Kontrakt

    7. Webhook-basierte Kommunikation¶

    Entscheidung: Webhooks für API → Discord Bot

    Begründung: - Entkopplung: API kennt keine Discord-Details - Skalierbarkeit: Asynchrone Kommunikation - Zuverlässigkeit: Retry-Mechanismen möglich

    Zusammenfassung¶

    ClansCore ist ein modulares, schichtenbasiertes System mit klarer Trennung der Verantwortlichkeiten:

    • Clean Architecture: Klare Schichtentrennung
    • Monorepo: Einheitliche Codebase
    • Type-Safety: TypeScript überall
    • Testbarkeit: Isolierte Komponenten
    • Erweiterbarkeit: Adapter-Pattern, Interfaces
    • Sicherheit: JWT, API Keys, Webhook Secrets
    • Skalierbarkeit: Docker-basiertes Deployment

    Die Architektur ermöglicht: - Einfache Wartung - Schnelle Entwicklung neuer Features - Hohe Code-Qualität - Gute Testbarkeit - Klare Dokumentation
